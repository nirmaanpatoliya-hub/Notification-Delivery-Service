How DakGhar Works

A deep dive into the transactional outbox pattern, background worker loop, retries, circuit breaking, and crash recovery.

1. Introduction & The Core Problem
What is DakGhar (डाकघर)?

DakGhar (Hindi for “post office”) is a reliable notification delivery service built using the Transactional Outbox Pattern. It decouples product code (such as e-commerce checkout or OTP generation) from third-party email and SMS providers.

The Problem: Why Direct Sending Fails

Most simple applications call third-party email or SMS APIs directly inside their HTTP web request. If the provider is slow or down, the user’s request hangs or crashes, and the notification is silently lost forever.

The DakGhar Solution

With DakGhar, when your app sends a notification, DakGhar saves it into an atomic SQLite outbox table and replies in milliseconds: 201 Accepted. A dedicated background worker loop takes responsibility for sending it, retrying temporary outages, switching to backup providers, and keeping an audit log of every attempt. Messages are persisted in the SQLite outbox so they can be retried after temporary failures or application restarts.

Simulated Delivery Architecture

DakGhar uses four internal mock providers:

  • Email: mailfast (Primary) & postbird (Backup)
  • SMS: smsly (Primary) & textgo (Backup)

Successful sends write to the simulated Fake Inbox. No real emails or SMS are sent outside the system.

2. End-to-End Notification Lifecycle

Here is what happens under the hood from the millisecond a notification is enqueued until it reaches final resolution:

1 Client Enqueues Message

Client calls POST /api/messages with channel, category, recipient, and message body.

2 Atomic Outbox Insertion

DakGhar validates inputs, inserts into the SQLite messages table as pending, and returns 201 Created in <10ms.

3 Worker Claiming (Tick)

Background worker runs every 1s, selects due pending messages (transactional first), and atomically claims them by transitioning status to sending.

4 Provider Selection

choose_provider() selects the highest-priority healthy provider, avoiding the provider that failed this message on its last attempt.

5 Mock Send & Attempt Log

The chosen provider attempts delivery. The result, timestamp, and any error message are recorded into the append-only attempts audit log.

6 Final Resolution

If delivered (ok), status moves to sent and enters the Fake Inbox. If transient error, retried with exponential backoff.

3. Message Status Machine

Every message in DakGhar is always in exactly one of four statuses. The status machine guarantees predictable, audited transitions:

pending

Saved in the SQLite outbox awaiting background worker pickup, or waiting out an exponential retry backoff window.

sending

Claimed by a worker thread for an active delivery attempt. Protected with a conditional lock so no duplicate attempts occur.

sent

Successfully delivered by a provider and written to the Fake Inbox. This is a terminal state.

failed

Permanent rejection (bounced address) or temporary errors that exhausted all 4 retry attempts. Contains detailed last_error.

Transition Trigger & Condition Resulting Behavior
pending → sending Worker tick runs; next_attempt_at ≤ now Message claimed with UPDATE ... WHERE status='pending'.
sending → sent Provider returns ok (success) Delivered copy inserted into inbox table; status finalized.
sending → pending Transient failure (attempt < 4) OR all providers cooling down Scheduled for retry with exponential backoff: now + 2^attempts seconds.
sending → failed Permanent failure (bounce) OR 4 attempts exhausted Immediately failed (no retry for bounce); or recorded as gave up after 4 attempts.
sending → pending (Crash Recovery) Application or worker restarts Any message left in sending state is reset to pending so it is never lost.
4. Retries & Exponential Backoff
Temporary vs. Permanent Failures
Permanent Error Address Bounces

Recipients ending in @bounce.example or phone numbers starting with +91900000 simulate nonexistent mailboxes or numbers. They fail immediately on attempt 1 with reason bounced: recipient does not exist. They are never retried.

Temporary Error Network Timeouts & Outages

A simulated provider outage (503 provider unavailable) or a simulated network timeout is temporary. The service pauses and retries using exponential backoff up to 4 attempts maximum.

The Exponential Backoff Schedule

Backoff delays grow exponentially according to the formula: next_attempt_at = now + 2^attempts seconds.

Attempt # Formula Wait Delay Action if Failed
Attempt 1 2^1 2 seconds Scheduled for Attempt 2
Attempt 2 2^2 4 seconds Scheduled for Attempt 3
Attempt 3 2^3 8 seconds Scheduled for Attempt 4
Attempt 4 MAX_ATTEMPTS 0s (Gave up) Marked failed: gave up after 4 attempts
5. Provider Failover & Circuit Breaker

To prevent hammering broken third-party services and avoid delaying customer messages, DakGhar implements a circuit breaker and automated provider failover:

Circuit Breaker Mechanics
  • Failure Threshold (OPEN_AFTER = 2): If any provider experiences 2 transient failures in a row, its circuit breaker trips (opens).
  • Cooldown Duration (COOLDOWN_S = 30s): When the circuit opens, the provider is quarantined for 30 seconds (open_until = now + 30).
  • Recovery Probing: After 30 seconds have elapsed, the provider is tried again. If the probe succeeds, consecutive_failures resets to 0. If it fails, the circuit re-opens for another 30s immediately.
  • Reset on Success: Any successful delivery (or legitimate bounce) immediately resets that provider's failure counter to 0.
Provider Choice & Failover Rules
  • Primary vs. Backup: Priority 1 providers (mailfast, smsly) are preferred when healthy. Priority 2 providers (postbird, textgo) act as hot standbys.
  • Avoid Last Failure: When choosing a provider for a retried message, choose_provider() skips the provider that failed this message on its previous try if another healthy provider is available.
  • All Providers Cooling Down: If both providers for a channel are in cooldown, the message is not failed! It remains pending with next_attempt_at = min(open_until), consuming zero retry attempts while waiting for a provider to wake up.
Provider Choice Decision Table (Email Channel Example):
mailfast (Primary) postbird (Backup) Avoid Provider Chosen Provider Explanation
Healthy Healthy None mailfast Both healthy, selects lower priority number (primary).
Healthy Healthy mailfast postbird Skips mailfast because it just failed this message; falls over to backup.
Cooling down Healthy None postbird Primary is in 30s cooldown; automatically routes to backup.
Cooling down Cooling down Any None (Wait) Both in cooldown; message waits until earliest cooldown expires without wasting attempts.
6. Crash Recovery & At-Least-Once Delivery
Surviving Server & Worker Crashes

What happens if the power is cut or the server crashes while messages are in-flight? Because DakGhar uses SQLite with immediate ACID transactions, messages are never lost in RAM:

UPDATE messages SET status = 'pending', next_attempt_at = now
WHERE status = 'sending'

Whenever the DakGhar server restarts, the worker's recover() routine immediately resets any message stuck in the sending state back to pending. Processing resumes seamlessly within one second.

Idempotency via Unique Constraints

The SQLite inbox table enforces UNIQUE(provider, message_id). If a crash occurred after the mock provider recorded delivery but before the message status was committed, the worker re-attempts delivery on reboot. The database's unique constraint prevents duplicate inbox records for the same provider and message. This supports safe retries after recovery, but does not guarantee that every message will ultimately be delivered.

SQLite Storage Architecture
  • messages: Primary outbox queue; tracks channel, recipient, body, status, attempts, backoff.
  • attempts: Immutable audit trail; one row per try recording timestamp, provider, result, error.
  • providers: Seeded provider configuration, failure rates, and circuit breaker state.
  • inbox: Fake delivered mailbox viewable on Screen 5.

Scenario B
Both SMS Providers Down: Exponential Backoff & Max Attempts

One OTP SMS enqueued at $t = 0\text{s}$ while both smsly and textgo are down. The message alternates between providers with exponential backoff until 4 attempts are exhausted:

Time Try # Provider & Reason Result Backoff Calculation & Next Action
0s 1 smsly (primary first) 503 smsly failures = 1. Backoff: $2^1=2\text{s} \rightarrow$ scheduled for $t = 2\text{s}$. Avoids smsly.
2s 2 textgo (avoids smsly) 503 textgo failures = 1. Backoff: $2^2=4\text{s} \rightarrow$ scheduled for $2 + 4 = 6\text{s}$. Avoids textgo.
6s 3 smsly (avoids textgo) 503 smsly failures = 2 $\rightarrow$ circuit opens until 36s. Backoff: $2^3=8\text{s} \rightarrow$ scheduled for $6 + 8 = 14\text{s}$.
14s 4 textgo (only healthy) failed textgo failures = 2 $\rightarrow$ circuit opens until 44s. Attempts reached 4 (MAX_ATTEMPTS). Status finalized as failed: "gave up after 4 attempts: 503 provider unavailable".
8. Key Concepts & Glossary
API (REST)

The interface that allows client applications to enqueue messages and query statuses over HTTP using JSON data.

Transactional Outbox

A distributed systems design pattern where outbound requests are saved into a database table first before being sent asynchronously.

Background Worker

An independent daemon thread executing a loop every second (tick()) to query, claim, and send due pending notifications.

Mock Provider

A simulated third-party gateway (like simulated Twilio or SendGrid) that prints delivery output and writes to the simulated Fake Inbox.

Exponential Backoff

A retry algorithm that exponentially increases wait times ($2\text{s}, 4\text{s}, 8\text{s}$) between failed attempts to prevent overloading failing services.

Circuit Breaker

A design pattern that temporarily disables routing to an external provider after 2 consecutive failures, protecting the system for a 30-second cooldown.

Provider Failover

Automatically redirecting notifications to an alternate provider (e.g., from mailfast to postbird) when the primary fails.

Idempotency

The property that executing the same operation multiple times produces the exact same outcome without causing duplicate deliveries.

Crash Recovery

The mechanism that automatically resets in-flight messages (sending → pending) on startup, achieving at-least-once delivery.

API Key Settings

DakGhar enforces permissions using two separate secret keys sent in request headers. Keys are stored only in sessionStorage for this browser session and sent to the DakGhar API in request headers (X-Api-Key or X-Admin-Key). They are cleared when the browser tab closes.

No Sender Key
Used for enqueuing messages and viewing the outbox and inbox. Sent exclusively via the X-Api-Key header.
No Admin Key
Used for worker pause/resume, single tick, provider outage switches, and database reset. Sent exclusively via the X-Admin-Key header.
